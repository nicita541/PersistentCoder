# План: PersistentCoder как рабочий end-to-end coding agent

## Цель

Пользователь открывает произвольную папку проекта, формулирует задачу обычным
языком (например: «создай файл, добавь функцию и тесты»), а PersistentCoder:

1. понимает задачу и ограничивает область изменений;
2. выполняет работу только в изолированной копии проекта;
3. запускает подходящие проверки;
4. показывает точный результат и причины возможного отказа;
5. после подтверждения безопасно переносит добавления, изменения и удаления в
   исходную папку;
6. после перезапуска не теряет состояние и не выдаёт незавершённую работу за
   успешную.

План считается завершённым только после прохождения автоматического
end-to-end сценария и воспроизводимого smoke-теста на отдельном тестовом
проекте. В headless-среде визуальный VS Code smoke заменяется сборкой extension,
проверкой webview JavaScript и запуском настоящего JSONL backend-процесса.

## Не входит в цель

- автономное изменение файлов вне выбранного проекта;
- применение непроверенных изменений;
- скрытый auto-apply в sandbox-режиме;
- обязательная зависимость от Git;
- выпуск публичного установщика или marketplace-релиза.

## Фаза 1. Зафиксировать пользовательский контракт

- [x] Описать один основной путь: выбор папки → ввод задачи → выполнение →
  проверка → preview → Apply/Discard.
- [x] Зафиксировать состояния, которые видит пользователь: `running`,
  `needs_attention`, `verified`, `failed`, `applied`, `discarded`.
- [x] Определить единый JSON-результат backend для CLI и VS Code: статус,
  краткое сообщение, изменённые пути, проверки, возможность Apply и причина
  блокировки.
- [x] Добавить понятные сообщения для отсутствующего Docker/model, невалидной
  задачи, конфликта исходников, устаревшей проверки и ошибки восстановления.

### Критерий готовности

CLI и VS Code используют одинаковые значения статусов и одинаково объясняют,
что произошло и какое действие доступно дальше.

## Фаза 2. Сделать verified-результат единственным источником Apply

- [x] При успешном завершении создать один immutable manifest из baseline и
  проверенного workspace и атомарно привязать его к сессии.
- [x] При `FAIL`, `BLOCKED`, отмене или падении не создавать применяемый
  manifest.
- [x] Строить preview из сохранённого manifest, а не из повторного сканирования
  «живого» workspace.
- [x] Показывать в preview операции `ADD`, `MODIFY`, `DELETE`, размеры и причины,
  по которым отдельный путь нельзя применить.
- [x] Перед Apply повторно доказать неизменность source, workspace, manifest,
  verification context и версии сессии.
- [x] Направить ручной Apply и Direct/auto-apply через один транзакционный
  сервис; старое прямое копирование файлов исключить из production-пути.
- [x] После успешного Apply пересоздать чистые baseline/workspace и перевести
  сессию в `CLEAN`; после конфликта сохранить результат для просмотра.

### Критерий готовности

Ни CLI, ни backend не могут применить файл, которого нет в сохранённом
verified-manifest; удаления работают так же, как добавления и изменения.

### Критерий готовности

Детерминированный fake-LLM выполняет набор типовых задач без ручного изменения
БД или внутреннего состояния runtime.
